# 游戏运行时性能预算

## 问题

刷怪时卡顿、地图灰屏或触控失灵通常是同一帧集中创建节点、导入纹理、计算路径和播放大量音效造成的。平均帧率不能揭示这种峰值，必须把预算落到生成、AI、寻路、渲染、网络和音频各阶段。

## 适用边界

本文面向中小规模实时游戏。具体毫秒、单位数和内存上限必须由目标设备实测后填写，不应把某个项目的数值复制为通用标准。

## 建立预算

使用[性能预算模板](../templates/performance-budget.template.json)记录目标设备、帧时间分位数、同屏实体、生成批次、路径查询、粒子、音频声道、纹理和网络快照预算。预算必须同时包含正常场景与峰值场景。

关键策略：

- **生成分批**：预加载资源，使用对象池，把单批创建限制在可测范围。
- **兴趣激活**：远离玩家的营地只保留轻量状态，进入兴趣半径才启用 AI、碰撞和动画。
- **寻路预算**：每帧只处理有限查询，相同目标复用路径，失败后退避重试。
- **缓存归属**：明确谁创建、谁复用、何时释放，避免每个单位重复缓存整图数据。
- **更新降频**：感知、目标选择、UI 和网络快照按需求频率更新，不必全部逐帧运行。
- **表现限流**：高攻速、溅射和群怪场景合并低优先级粒子、飘字与音效。

## 性能证据

每次优化要保留场景、版本、设备、采样时长、帧时间曲线和事件标记。把“开始刷怪”“首个路径请求”“资源首次加载”标在采样中，才能区分资源导入、脚本和 GPU 峰值。

## 常见失败

- 只在空地图测平均 FPS，不测正式资源和峰值生成。
- 每个怪物在同一帧计算全局路径并扫描全部目标。
- 运行时反复加载同一图片或创建材质。
- 用永久存活对象池换取短期流畅，却没有容量和回收策略。
- 优化后不记录对照数据，只凭主观判断。

## 自动检查

- 压力场景按固定种子生成固定数量对象。
- 采集帧时间分位数、最长帧、内存峰值、节点数和路径队列长度。
- 检查单帧生成数、对象池上限和网络快照字节数不超预算。
- 检查资源加载发生在预加载阶段，而非首次命中帧。
- CI 保存机器可读报告并与允许回退阈值比较。

## 人工检查

- 在最低目标设备上从冷启动进入峰值场景。
- 同时移动、释放技能、开面板，观察输入是否仍有响应。
- 持续运行后检查温度、降频、内存增长和音效破裂。
- 用正式纹理、正式动画和真实网络设备复测。

## 验收标准

### 最低验收

- 有明确目标设备和峰值场景。
- 刷怪、路径与表现均有上限，主线程不会一次完成全部工作。
- 自动报告能定位最长帧发生在哪个阶段。

### 正式验收

- 目标设备长时运行满足预算分位数与内存上限。
- 冷启动、集中刷怪、高攻速群伤和远程联机均有性能证据。
- 每次预算调整记录原因、影响和回退基线。
