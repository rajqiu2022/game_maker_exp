# 新项目采用指南

这份指南用于把经验库的一部分接入新游戏，不要求一次采用全部内容。

## 1. 先选一个真实问题

不要为了“统一”而整体搬运。先从当前阻力最大的专题开始：

- 地图经常手改且容易破坏：采用地图规格和构建管线。
- 角色进入建筑后被完全挡住：采用建筑遮挡契约。
- 技能代码里塞满特效和音效分支：采用技能表现解耦。
- 怪物有黑底、脚底跳动或没有攻击动作：采用精灵动画契约。
- 手机按钮经常点不到：采用 UI 语义/布局/输入三层模型。
- 远程玩家状态和交互失效：采用请求、权威结果、状态修订和本地 UI 边界。
- 刷怪或高攻速战斗卡顿：先建立目标设备峰值预算，再分批生成和限流。
- 前期没有可打造装备：采用职业路线、过渡层级和可达性测试。
- 不同平台包内容不一致：采用入口资源闭包和包后审计。
- 音效缺失或群战爆音：采用语义事件、阶段拆分和并发组。

## 2. 复制模板，不复制示例 ID

从 `templates/` 复制到项目自己的配置目录，然后完成三件事：

1. 把 `example_*` ID 替换成项目稳定 ID。
2. 把资源路径改成项目相对路径，禁止机器绝对路径。
3. 删除不需要的 `_comment`，保留 `schema_version`。

不要直接引用本仓库模板作为游戏运行时文件。项目应拥有自己的副本，避免公共仓库更新导致构建突然变化。

## 3. 建立项目适配层

推荐让业务代码只认识项目自己的接口：

```text
公共模板概念
    ↓ 项目转换/加载器
项目内部数据模型
    ↓
引擎运行时节点与资源
```

例如，公共技能表现模板中的 `cast.vfx_id` 可以转换为 Unity Addressable、Godot `res://` 路径或自研资源句柄。不要让公共文档决定项目底层资源系统。

## 4. 从最低门禁开始

第一周至少建立：

- JSON/配置可解析。
- 所有被引用资源存在。
- ID 不重复。
- 关键场景能由引擎无界面加载。
- 目标设备上完成一次人工交互验收。
- 联机项目至少用双实例验证一个权威状态往返。
- 正式包至少审计一个可玩入口的资源闭包。

成熟后再增加透明通道、锚点波动、动画帧差异、触控命中区和性能预算等检查。

## 5. 记录差异，不修改公共含义

如果项目需要额外字段，先在项目模板中扩展。经过实际验证后，再按[贡献规范](../CONTRIBUTING.md)提交到公共仓库。

适合回馈的经验包括：

- 同一失败在两个项目重复出现。
- 新字段能消除硬编码分支。
- 新检查在发布前抓住了真实问题。
- 平台差异证明原规则的适用边界不完整。

## 6. 建议的项目内目录

```text
game-production/
├── specs/          可编辑规格
├── generated/      可重新生成的产物
├── manifests/      美术、动画、音频契约
├── previews/       地图和 UI 审阅产物
├── qa/             机器可读报告
└── docs/           项目差异与案例
```

`generated/` 是否进入版本库由团队决定，但无论是否提交，都不能成为唯一数据源。

专题模板可按需求加入：

- 联机：`network-state-envelope.template.json`
- 性能：`performance-budget.template.json`
- 装备：`equipment-route.template.json`
- 发布：`release-profile.template.json`
- 音频：`audio-presentation.template.json`
- 资源共享：`resource-pack.template.json`

## 7. 完成判定

一次采用只有在以下条件同时满足时才算完成：

- 新成员能找到源规格和生成命令。
- 删除生成目录后可以重建。
- 自动检查能拦住至少一种已知错误。
- 目标设备上的视觉、输入或动画问题确实改善。
- 项目差异被记录，而不是藏在加载器的特殊分支里。
- 性能、联机或跨平台专题采用后，能够指出对应的自动证据与真实设备结果。
