# 多人联机权威状态

## 问题

联机故障往往不是“少同步一个字段”，而是请求、结算、状态和本地界面混在一起。远程玩家可能学会技能却不能释放，拾取成功却看不到背包变化；一个玩家打开建筑，所有客户端都弹出面板。解决这些问题需要先定义谁有权改变什么。

## 适用边界

本文适用于房主权威或服务器权威的合作游戏。输入预测、回滚和主机迁移属于更高成本能力，应单独立项；即使暂不支持，也必须有断线检测、清晰提示和安全返回流程。

## 状态边界

一次操作按以下链路流动：

1. **Command**：本地输入意图，例如按下技能槽。
2. **Request**：带玩家、对象、序号和参数的网络请求。
3. **Result**：权威端校验后产生的一次性结果，如扣除材料。
4. **State**：可恢复的权威快照，如等级、背包、基地生命。
5. **Presentation**：可重放表现事件，如命中特效和拾取音效。
6. **Local UI**：只属于当前设备的面板、选中项和拖拽状态。

客户端不能直接修改权威背包、等级或世界对象。权威端也不应广播“打开商店面板”这种本地 UI 指令，而是返回交互成功及可展示数据，由请求者本地打开。

## 版本、去重与恢复

- 每个请求携带 `request_id`，服务端缓存近期结果，重复请求返回同一结果。
- 每个可恢复对象携带单调递增 `revision`；客户端拒绝旧修订。
- 表现事件携带 `event_id` 与来源修订，客户端按事件 ID 去重。
- 加入或重连先收完整快照，再接收增量；快照完成前禁用依赖状态的按钮。
- 当前地图的兼容摘要单独交换，不因设备缺少未参与联机的其他地图而拒绝加入。
- 心跳超时进入“连接异常”状态，UI 明示重试、等待或退出，不让角色无提示冻结。

可复制的数据骨架见[网络状态信封模板](../templates/network-state-envelope.template.json)，发布前使用[多人联机检查表](../checklists/multiplayer-release.md)。

## 常见失败

- 客户端先改背包，再等待主机确认，失败时无法可靠回滚。
- RPC 只同步动画，没有同步等级、装备或技能槽的权威修订。
- 重复包导致二次购买、二次扣料或二次播放掉落提示。
- 节点路径或连接顺序被当成稳定玩家身份。
- 世界交互候选由主机保存，远程触控点击时没有重新校验目标。
- 断线后继续显示可操作 HUD，使玩家误以为技能失效。

## 自动检查

- 请求处理测试覆盖合法、越权、过期、重复和对象已失效。
- 状态序列化往返后字段、类型和修订不变。
- 同一 `request_id` 处理两次只产生一次资源变化。
- 乱序增量不能覆盖更新快照。
- 本地面板事件不会出现在网络广播协议中。
- 双实例集成测试覆盖技能、装备、拾取、建筑、商店、入口和基地失败。

## 人工检查

- 用不同平台的两台真实设备持续联机，分别轮流担任远程玩家。
- 对每个交互观察请求者、其他玩家和权威端三处结果。
- 模拟短时丢包、切后台和恢复网络，确认提示及状态收敛。
- 主机退出时验证产品声明：迁移、重连或明确结束房间。

## 验收标准

### 最低验收

- 权威端唯一结算；重复请求不重复生效。
- 等级、基地生命、技能槽、装备和背包在远程端最终一致。
- 建筑和商店面板只在操作玩家本地打开。
- 断线有提示，失败后可安全返回。

### 正式验收

- 完整快照与增量修订可在乱序、重复和短时断网后收敛。
- 两种目标平台完成长时双实例流程并保留日志。
- 当前联机地图按依赖闭包校验，兼容失败能指出具体资源或协议差异。
